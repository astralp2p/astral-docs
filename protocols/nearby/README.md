# nearby

The `nearby` protocol lets nodes on one local network find each other with no address configured. A node broadcasts a [`mod.nearby.status_message`](types/mod.nearby.status_message.md) over [`ether`](../ether/README.md), and every node that receives it caches the sender. A node broadcasts a [`mod.nearby.scan_message`](types/mod.nearby.scan_message.md) to ask the other nodes for their status. nearby discovers nothing beyond the local network.

[`mod.nearby.mode`](types/mod.nearby.mode.md) decides what a node sends, and lists what each mode discloses:

* `0` (Silent) sends no nearby datagram. The node still receives.
* `1` (Visible) sends a [`mod.nearby.public_profile`](types/mod.nearby.public_profile.md) with the node identity, the user identity and the node alias. A node without an owner sends a [`mod.nearby.flag`](types/mod.nearby.flag.md) reading `adoptable` before the profile, and its profile names no user.
* `2` (Stealth) sends a [`mod.nearby.stealth_hint`](types/mod.nearby.stealth_hint.md), which only a node that knows the node identity or the user identity reads. A node without an active contract has no user identity and acts in Visible instead, unless its stored mode is Silent.

A node whose `tcp` listen port is not `1791`, or whose `kcp` listen port is not `1792`, also sends its listen ports: in Visible a [`mod.nearby.listen_ports`](types/mod.nearby.listen_ports.md) after the profile, in Stealth a [`mod.nearby.sealed_ports`](types/mod.nearby.sealed_ports.md) after the hint. The sealed ports open only with the node identity and the hint's nonce. A port is `0` when the node has no such transport. A node on both default ports sends no port object.

The node's registered `Composer` implementations build these attachments. nearby then appends a [`mod.nearby.status_proof`](types/mod.nearby.status_proof.md) as the last attachment: the node key's signature over the other attachments, a nonce and the sender's time. When the status holds a `mod.nearby.stealth_hint`, which is the Stealth mode, the signature is wrapped with a key derived from the node identity. A status carries no address, no contract and no `mod.dir.alias`.

A node broadcasts its status every 85 to 95 seconds, the interval drawn uniformly at random each time. It also broadcasts its status when its mode changes, when it gains a local address, on [`nearby.broadcast`](ops/nearby.broadcast.md), and in reply to a scan. [`nearby.scan`](ops/nearby.scan.md) broadcasts a scan. A node answers a scan by broadcasting its normal status on the one local subnet that contains the scan's source IP. It answers at most once per 2-second window on each subnet. A scan inside the window schedules one broadcast at the end of the window, unless one is already scheduled. A node never answers a scan by unicast, and does not answer a scan whose source IP lies in none of its subnets.

A node processes a received status in this order. It caches the sender as identified, and acts on it, only when every step passes:

1. Shape: the attachments hold exactly one `mod.nearby.public_profile` or exactly one `mod.nearby.stealth_hint`, not both. The last attachment is a `mod.nearby.status_proof`, no other attachment is one, and its `Sig` is 8 to 72 bytes.
2. Freshness: the proof's `Timestamp` is at most 5 minutes before or after the receiver's clock.
3. Cache room: the cache holds one entry per cache key and at most 512 entries. The cache key is the source IP and the `tcp` listen port of the status, `1791` when the status carries no ports. While the cache is full, a status from a source IP that holds no entry is dropped here, so a node that moves to a new source IP is refused until an entry expires. A status from a source IP that holds an entry passes this step and is dropped when it would be stored under a new cache key, at step 4 for an unrecognised status and at step 7 for a verified one. A status under an existing cache key is accepted, and so is a verified status of a node that moves to another `tcp` port at such an IP, because its old entry is removed first and frees a slot.
4. Identify: the node's registered recognizers try the status in turn, and the first that recognises it names the node identity and, when known, the user identity. The `user` module recognises the node's own user, in a stealth hint and in a profile whose `UserID` is that user. On a node without a user, while [`user.join`](../user/ops/user.join.md) runs, the `user` module recognises a stealth hint that opens with the identity of the node being joined, and names that node and the hint's user. When no recognizer matches, a Visible status names the node and the user through its `mod.nearby.public_profile`. A Stealth status that no recognizer matches is cached with its source IP only, as an unrecognised node, under the cache key of its source IP and the default `tcp` port `1791`, and processing stops. Such a status is dropped when a live verified entry holds its source IP on port `1791`; it is accepted beside a verified entry that uses another port, and replaces only an unrecognised or expired entry under its cache key. While the cache is full, it is dropped here when its cache key holds no entry.
5. Replay: the proof's `Nonce` is not remembered for the same node identity. The receiver remembers each nonce until 5 minutes after the proof's `Timestamp`, by the same clock as the freshness check, so a status stamped ahead of its arrival is remembered for up to 10 minutes. The receiver remembers at most 32 live nonces of one node and drops a status of a node at that bound. The memory holds at most 16416 nonces, 32 for each of 513 nodes. When the memory is full, the receiver forgets the nonces of every node without a live cache entry, except the node of the status in hand.
6. Verify: the receiver unwraps the signature of a Stealth status, and the signature verifies against the key of the identified node.
7. Accept: the receiver remembers the nonce and caches the node identity, the user identity, the source IP, the listen ports and how the node was identified. The ports are those of the one `mod.nearby.listen_ports` of a Visible status, or of the one `mod.nearby.sealed_ports` of a Stealth status opened with the identified node identity and the hint's `Nonce`. The receiver caches no ports, and keeps the status, when the status holds more than one port object, a port object of the other mode, or a `mod.nearby.sealed_ports` whose `Data` is not 4 bytes. It emits a [`mod.nearby.peer_seen`](types/mod.nearby.peer_seen.md) event when the node is new to the cache, when its source IP changed, when its user identity changed (for example, the node was claimed), when its listen ports changed, or when it returns after its entry expired. The listen ports are the effective ones: a status without ports and a status with `1791` and `1792` are the same ports. A node holds one entry: caching its verified status removes its entry under any other cache key, so a node that moves to another source IP or `tcp` port leaves no stale entry. A repeated status that changes none of these emits nothing.

A cache entry expires 5 minutes after it was last updated, and the node removes expired entries periodically. [`nearby.list`](ops/nearby.list.md) lists the cache.

For a verified cache entry the node resolves two endpoints of the peer: `tcp` at the source IP on the entry's `TCP` port, and `kcp` at the source IP on its `KCP` port. An entry without ports uses `1791` and `1792`. A port of `0` gives no endpoint for that transport. The endpoints stay valid for the rest of the entry's life. The node resolves no endpoint for an unrecognised entry. Nodes on one host broadcast from one source IP, hold one entry each under their own `tcp` ports, and resolve each to its own ports; two nodes on one host that announce the same `tcp` port share a cache key, as do two that announce `tcp` port `0`. The node resolves an alias `.name` to the verified peer whose `mod.nearby.public_profile` names the alias `name`.

The [`user`](../user/README.md) module acts on a `mod.nearby.peer_seen` only when it names the node's own user. It links at once to such a peer that is a swarm member and is not linked. It links to any other such peer, reads the peer's contract with [`user.contract`](../user/ops/user.contract.md), checks it, and introduces the node to the peer only when the check passes. Unowned nodes and nodes of other users are only cached and listed.

`silent_listen` in `nearby.yaml`, the tree value `/mod/nearby/silent_listen`, decides whether a Silent node acts on what it hears. It defaults to `true`, and a Silent node then contacts peers of its own user by the same rules as in the other modes. When it is `false`, a Silent node caches and lists peers but emits no `mod.nearby.peer_seen`.

nearby needs roughly synchronised clocks. The other nodes drop the statuses of a node whose clock is more than 5 minutes off. A device with no battery-backed clock and no time server cannot be found through nearby. Such a device joins through [`user.join`](../user/ops/user.join.md) over a link the swarm node opens to it, or is claimed.

Three ops are exposed, each gated by [`mod.auth.admin_network_action`](../auth/types/mod.auth.admin_network_action.md): `nearby.broadcast` broadcasts the node's status now, `nearby.scan` asks the local network for statuses, and `nearby.list` streams the cache.
